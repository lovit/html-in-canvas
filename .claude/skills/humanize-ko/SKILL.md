# humanize-ko

한국어 텍스트를 읽기 쉽게 고쳐 쓴다. 목표는 **쉬운 말로 정확하게** 다. 쉽게 쓴다고 뜻이 흐려지면 실패고, 정확하게 쓴다고 문장이 굳으면 그것도 실패다.

## 입력 처리

- 인자가 파일 경로면 그 파일을 읽어 고치고, 무엇을 왜 바꿨는지 요약해 보고한다
- 인자가 텍스트면 고친 결과를 돌려준다. 파일을 만들지 않는다
- 인자가 없으면 무엇을 다듬을지 물어본다
- 여러 파일이면 파일마다 따로 처리하고, 마지막에 한 번만 요약한다

## 고칠 것

### 1. 번역투

영어 문장 구조를 그대로 옮긴 표현을 우리말 어순으로 되돌린다.

| 고치기 전                             | 고친 뒤            |
| ------------------------------------- | ------------------ |
| 이 API 에 대한 설명을 제공합니다      | 이 API 를 설명한다 |
| 플래그를 통하여 활성화됩니다          | 플래그로 켠다      |
| 에러가 발생되어질 수 있습니다         | 에러가 날 수 있다  |
| 다음과 같은 방법을 사용할 수 있습니다 | 이렇게 하면 된다   |
| ~하는 것이 가능합니다                 | ~할 수 있다        |
| ~라고 말할 수 있습니다                | ~다                |
| 개발자로 하여금 ~하게 합니다          | ~할 수 있다        |

### 2. 명사로 늘린 문장

동사로 쓸 수 있는 것을 명사 + 하다로 늘리지 않는다.

| 고치기 전                    | 고친 뒤         |
| ---------------------------- | --------------- |
| 최적화의 수행이 요구됩니다   | 최적화해야 한다 |
| 확인을 진행합니다            | 확인한다        |
| 렌더링의 처리가 이루어집니다 | 렌더링한다      |
| 설치가 완료되면              | 설치가 끝나면   |

### 3. 근거 없는 수식어

"혁신적인", "강력한", "매우 중요한", "놀라운", "완벽한" 같은 말은 정보가 없다. 지우거나, 왜 그런지를 대신 적는다.

| 고치기 전                     | 고친 뒤                                                      |
| ----------------------------- | ------------------------------------------------------------ |
| 매우 강력한 기능을 제공합니다 | 텍스트 레이아웃을 직접 구현하지 않아도 된다                  |
| 혁신적인 접근 방식입니다      | 기존 foreignObject 해킹과 달리 폰트와 CSS 가 그대로 적용된다 |

### 4. 문장 쪼개기

한 문장에 여러 뜻이 들어 있으면 나눈다. 접속사로 이어 붙인 긴 문장이 특히 그렇다. 다만 짧은 문장만 늘어놓으면 끊긴 느낌이 나므로, 긴 문장과 짧은 문장을 섞는다.

### 5. 빈 접속사

"그리고 나서", "또한", "따라서" 를 습관처럼 붙이지 않는다. 앞뒤 관계가 이미 드러나면 지운다.

### 6. 형식 과잉

- 불릿으로 쪼갤 필요 없는 내용을 불릿으로 만들지 않는다. 이어지는 설명은 문단으로 쓴다
- 이모지를 장식으로 쓰지 않는다
- 굵게 표시를 남발하지 않는다. 다 강조하면 아무것도 강조되지 않는다
- 제목만 있고 내용이 한 줄인 섹션을 만들지 않는다

### 7. 하드랩

문단 안의 줄바꿈을 모두 없애 한 줄로 잇는다. 리스트 항목, 표의 행, 코드 블록, 인용문, 제목의 줄바꿈은 그대로 둔다. 자세한 규칙은 @.claude/rules/writing-style.md 에 있다.

## 건드리지 말 것

- **API 이름, 클래스 이름, 플래그 이름, 파일 경로, 명령어**: `drawElementImage`, `layoutSubtree`, `--enable-blink-features=CanvasDrawElement` 는 한 글자도 바꾸지 않는다
- **전문 용어의 원어**: hit testing, origin trial, texture, shader 처럼 원어가 표준인 말은 억지로 번역하지 않는다. 대응표는 @docs/glossary.md 에 있다
- **코드 블록과 인용문 안의 내용**
- **숫자, 버전, 날짜, 링크**
- **문체(존댓말/평서체)**: 원문이 "~합니다" 면 "~합니다" 로, "~다" 면 "~다" 로 유지한다. 사용자가 바꿔 달라고 할 때만 바꾼다
- **사실 관계**: 문장이 매끄러워진다고 해서 없던 단정을 넣지 않는다. "~일 수 있다" 를 "~이다" 로 바꾸지 않는다

## 판단이 서지 않을 때

원문의 뜻이 두 가지로 읽히면 마음대로 고르지 말고 그대로 두고 물어본다. 다듬는 일이 뜻을 바꾸는 일이 되면 안 된다.

## 결과 보고

파일을 고쳤으면 이렇게 보고한다.

1. 바꾼 문장 수와 주된 유형 (번역투 n건, 명사화 n건, 하드랩 n건)
2. 뜻이 달라질 수 있어 건드리지 않은 곳이 있으면 그 위치와 이유
3. 마크다운 파일이면 `node scripts/check-hard-wrap.mjs <파일>` 을 돌려 통과를 확인한 결과

## 전체 예시

### 고치기 전

```markdown
## 개요

본 문서는 HTML-in-Canvas API 에 대한 개괄적인 설명을 제공합니다. 해당 API 는 매우 강력한 기능으로서, 개발자로 하여금 DOM 엘리먼트를 캔버스 내부에 렌더링하는 것을 가능하게 합니다. 또한, 이를 통하여 접근성의 확보가 이루어질 수 있습니다.
```

### 고친 뒤

```markdown
## 개요

이 문서는 HTML-in-Canvas API 를 설명합니다. 이 API 로 DOM 엘리먼트를 캔버스 안에 그릴 수 있습니다. 그린 뒤에도 엘리먼트가 DOM 에 그대로 남아 있어서 스크린리더가 읽고 키보드 포커스가 들어갑니다.
```

마지막 문장을 눈여겨보자. "접근성의 확보가 이루어질 수 있습니다" 는 무슨 일이 일어나는지 말하지 않는다. 고친 문장은 실제로 무엇이 되는지 적는다. 쉬운 말로 쓰는 일은 대개 더 구체적으로 쓰는 일이다.
